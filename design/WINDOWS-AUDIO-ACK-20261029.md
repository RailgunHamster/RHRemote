# 状态回退期间的声音控制回执

Windows `0.2.11-preview.93` 修复已确认成功的声音／音量操作被旧首帧缓存覆盖的问题。它是 [preview.92 首帧状态回退修复](WINDOWS-FIRST-FRAME-STATE-20261029.md) 的后续修正；两者都没有解决 UI 从未确认初次首帧的旧失败，也不代表实际声音播放已经验收。

## 原因与修改

preview.92 在状态接口短暂不可用时，保留同次存活子进程已确认的首帧、窗口句柄及有限声音字段。但声音控制返回成功后，没有更新这份回退记录。下一次读取早期文件时，成功设置的 37% 被缓存中的 100% 覆盖；缓存若保存开关旧值，也有同样的问题。

新增 localhost HTTP／真实子进程回归先在未修改生产实现时运行，13 项中 **11 通过、2 失败**，分别复现音量和开关成功回执被覆盖。最终 preview.92 候选包也在实际 winserver 会话复现：音量请求得到成功回执，之后经过 3 次记录恢复，界面却显示 100%，断言要求 37%。`baseline-light01` 明确失败，日志未覆盖。

preview.93 在发送控制前记录当前持有子进程的 PID 和本次启动标识；不持锁等待网络。收到 `ok:true` 后，重新核对该子进程仍存活、PID 和启动标识均一致，才更新当前首帧记录及本次连接参数中的声音字段。失败回执不修改记录；旧启动的迟到回执即使 PID 相同，也不能更新新会话。没有修改系统音量或日常保存配置。

新增 4 项声音回归覆盖成功开关、成功音量、拒绝回执及同 PID 新交接后的迟到回执。最终核心 **129**、Windows UI **208** 项通过，另有 **1** 项既有 UIA 用例忽略。第一次完整编译因可变借用写在 match guard 中失败，修正后才运行最终回归；编译失败不计作行为证据。

## 最终候选包的实际复验

证据根目录：`D:\RHRemoteTools\ui-audio-ack93-review-20261029`。使用解包后的最终 preview.93 候选，在实体副屏 `DISPLAY2` 连接 winserver 的既有物理主屏；1080p30／25 Mbps／H.264／硬解，声音保持关闭。没有操作 OPPO。

读取故障通过既有隔离预览专用接口有限注入，只使父客户端状态读取返回明确的 `test_unavailable`；实际音量请求仍发往真实原生引擎。它不改变网络、状态文件或服务器，因此不能代替断网及整个控制接口失效的验收。

最后两轮改为直接核对实际 selectedDisplay 的可用、物理、主屏及 GDI 字段。每轮实际控制页按钮派发 9 次，音量成功设为 37%，再等待至少 3 次故障回退，仍显示 37%，声音保持关闭、会话保持连接。实时读取恢复后派生首帧标记消失。各完成 40／40 次并发状态请求，最大 11／14 ms；该数字是本轮控制读取耗时，不是首帧或画面时延。

`audio-volume-acknowledged.png` 为应用自身窗口绘制，已逐一查看浅深色的声音页：37% 与关闭状态完整可见，没有裁切。`keyboard-state-blip.png` 保留读取故障期间的自身键盘绘制。图中黑色背景不表达系统合成的透明度，也不包含远端画面。

这两轮退出均收到正常断开确认，分别 802／547 ms，`forced:false`。六轮最终清理核对保留失败结果：所有临时 UI、原生进程及已运行的源探针已结束，任务不存在；没有绕过空闲、前台归属或修饰键保护来凑齐按键通过。preview.93 完整输入复验仍待完成。
