# 原生 60 FPS 输入与播放器等待定位

日期：2026-10-25。范围为 winserver 的现有 LG FULL HD 物理屏、Windows 客户端及真实影片输入。
用户允许本机主屏测试，OPPO 仍暂停。所有测试静音，后台业务未暂停，未修改驱动、BIOS 或虚拟机资源。

## 结论与边界

此前 software / H.264 / LAN 25 Mbps 的两段 1080p30 输出约 29.986 / 30.005 FPS，记录见
[编码等待调查](ENCODER-HARDWARE-WAITS-20261025.md)。本轮继续保留该默认路径。

首轮原生 1080p60 串流输出约 55.923 FPS，但影片播放器自身丢帧 7.323%，超过原定 1% 门槛。
随后停止串流，播放器单独播放仍丢帧，因而不能把首轮结果当作有效的远程 60 FPS 验收，
也不能把全部差距归到客户端、网络或软件编码器。没有放宽门槛或关闭源丢帧检测。

进一步已在播放器主线程的实际原始栈中定位到 D3D9 Present → Intel 用户驱动 → 系统条件变量等待，
并核对到驱动机器码及导入表。它说明测试输入的显示路径存在独立等待；具体进度依赖与唤醒来源仍需继续查。
这不是将此前 QSV / MF 的等待宣布解决，也不是证明这些路径已不可优化。

后续已建立通过原门槛的浏览器真实影片输入：独立播放 59.968 FPS、零新增丢帧，
串流期间 59.968 FPS、丢帧 0.265%。后者对应的远程输出仍为 56.214 FPS。
逐帧已确认默认两个线程下，颜色转换与软件编码串行平均 17.187 ms，
约 49.47% 的新输入帧超过 60 FPS 的 16.667 ms 预算。
四线程限时试验缩短了这段跨度，但源丢帧和重复输入仍未过关，原配置已恢复。
详见 [浏览器输入与软件编码预算](BROWSER60-SOFTWARE-BUDGET-20261025.md)。

## 素材与首轮串流

素材来自 [Blender 官方原生 1080p60 影片](https://download.blender.org/demo/movies/BBB/bbb_sunflower_1080p_60fps_normal.mp4.zip)，
署名 Blender Foundation，CC Attribution。没有插帧或重编码。

- 文件：`bbb_sunflower_1080p_60fps_normal.mp4`，355856562 字节。
- ffprobe：1920×1080，`avg_frame_rate = 60/1`。
- SHA256：`3AA2D8946EC7CF3B50B7148FB3338CA421E6EC34987B20A4044845D674794E3E`。
- 物理屏刷新率由 QueryDisplayConfig 在交互会话读回：14850000 / 247500 = 60 Hz，未改显示模式。

首轮 software60a 请求 H.264 / 1920×1080 / 60 FPS、LAN 25 Mbps、分包 1024、静音，
完整 launch manifest 确认实际请求和源文件均为 60 FPS。
约 60.443 秒记录中，捕获回调 55.635 FPS、输出 55.923 FPS、客户端 render_return 55.921 FPS；
通用 encode 调用平均 9.874 ms、P99 16.662 ms，输出间隔 P99 27.203 ms、最大 33.747 ms。
实际首帧提交 1.407 秒，轮询发现首帧为 1.748 秒，两者端点不同。

播放器同期新增丢帧 274，丢帧比例 7.323%，时钟倍率 1.000195。
只保留为 source-invalid diagnostic，`performanceAccepted = false`。
软件编码内部 API 尚未分段，不能将 unknown 当作零耗时。
输出帧率也不是独特画面帧率或物理 scanout 帧率。

全部未通过源门槛。CPU 指标是进程 CPU 时间除以墙钟时间，不是整机利用率。
业务负载没有受控，各轮是顺序观察，不能用这些数值宣称某设置有固定因果增益。
滤镜线程限制确实减少该次进程 CPU 开销，但没有带来合格的 60 FPS 输入，因此没有应用到远程产品参数。

04 因测试脚本布尔值状态上报错误未就绪，没有有效测量；原 FAIL 保留，任务及播放器不存在的独立清理证明已保存。
06 是下述带 WPR 的定位轮，丢帧 17.320%，不混入无剖析的性能对照。
10 的前后前台 PID 从播放器自身变为其他进程；这不等于已经证明窗口被完全遮挡，
11 的置顶对照仍未合格，也不能把遮挡当作全部原因。

[FFplay 源码](https://github.com/FFmpeg/FFmpeg/blob/n8.1/fftools/ffplay.c)说明默认 SDL 渲染会请求垂直同步，
禁用音频后默认时钟回退到外部时钟；实际 verbose 日志确认原后端为 `direct3d`，03 为 `direct3d11`。
10 / 11 使用 `-sync video -framedrop`，显式保留丢帧检测；没有用默认视频时钟关闭丢帧来制造合格结果。
播放器自报时钟和丢帧仍不能证明每一帧都实际呈现。

## 原始线程、符号与机器码

06 仅播放真实影片，不建立远程会话，使用已有 CPU 剖析 profile。
独立 90 秒清理任务在开始前装好，正常测量约 30 秒后停止；实际 ETL 覆盖约 34.54 秒。
录制开销单独保留，不能将它当作正常播放基线。

- 原 ETL：159295956 字节，SHA256 `0095EFB80549019A762C2AE4B023A655150C9C0585D59ECB20CC8B89EAC1259D`。
- 7,212,011 个事件、3,305,229 个 StackWalk；原始头部事件／缓冲丢失为零。
- 播放器 PID 29776 的实际模块在开始时记录；导出的源进程原始栈 481,831 条，读取零错误。
- 主呈现线程 TID 49304 的 28,808 条原生切换与独立 xperf 解码全部逐条对应：线程、CPU、时间一致。
  64 个时钟锚点偏差范围 0.9002 微秒。经典 CSwitch 的 TDH 元数据不可用，失败尝试保留；
  原始候选布局经全部 28,808 条独立解码验证后才使用，没有把元数据缺失伪装为成功。
- 内核／用户栈片段分别保存，在相同原始切入 QPC、CPU、载荷 PID／TID 处匹配，不拼造调用链。

主线程闭合区间 CPU 约 4.075 秒，离 CPU 约 30.456 秒。
其中带图形调用链的离 CPU 区间合计约 7.032 秒，最长 52.989 ms；其余包含正常节拍及未分类等待，
不能把全部离 CPU 时间都称为性能损失，更不能将其当作 GPU 指令执行时间。

最长图形等待的用户栈对应 D3D9 的 `Present` / `PresentMain` / `DdBltLH`、Intel 驱动，
再进入 `SleepConditionVariableSRW` / `RtlSleepConditionVariableSRW` / `ZwWaitForAlertByThreadId`。
五个实际目标映像的首尾 rundown、加载地址、尺寸及校验和与拷出的 PE 文件逐一核对。
完整映像读取器有两条其他记录无法解码，未称为全局零错误。

公共符号从微软服务器取得，PE RSDS 的 GUID、DBI age 与 PDB 匹配。
公开剥离 PDB 的 Info age 为 3 / 4、DBI age 为 1，具体字段均保存；未将 Info age 冒充匹配。
原 DbgHelp 辅助工具出现错误 126，未使用其失败结果；LLVM 公共符号解码与 PE 导出另行核对。
Intel 私有函数名称保持未知。

实际 `igd9trinity64.dll` 版本 32.0.101.8864，SHA256
`E117667EFC5EB0DA2F618771E273E574DE9DB205C6F92BBD746E19EB2BD283F4`。
栈中的返回 RVA `0xe252c0` 对应下列实际指令：

```text
e252a0  mov rax, [rdi+0x28]
e252a4  cmp rax, rbx
e252a7  jae e252f4
e252b0  mov r8d, 0x64
e252ba  call [SleepConditionVariableSRW 的实际 IAT 项]
e252c0  test eax, eax
```

这段代码等待内部进度计数满足条件，调用时单次超时参数为 100 ms。
运行时函数表覆盖的 161 字节代码区域 SHA256 为
`0676AA05C3E6BCCC7A638A6F40592C94E8A598BEFE0147B11F754116775F1ABD`；
它有 chained unwind，连接到 `0xe25250–0xe2527c` 的父区域，未称为完整函数。
区域内还实际调用 SRW 锁及零超时 `WaitForSingleObject`；完整字节与反汇编保留。
没有修改驱动，没有把内部计数对象猜作特定显存缓冲或已知 fence。
