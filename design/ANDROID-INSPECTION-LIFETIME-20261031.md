# Android 检查取消、过期反馈与耗时对照

2026-10-31，本地候选 **0.2.11-preview.153 / 371**。本轮沿用现有设备工作区，修正检查任务结束的判断及配置变化后的反馈；没有操作 OPPO、升级日常客户端或公开发布。

## 行为与原因

旧代码将 Future 的取消视为探测已结束。但取消只能使 Future 进入终态，正在执行且不响应线程中断的调用仍可能继续，例如系统 DNS。这时提前释放检查归属和通道，会让下一次连接与旧探测交叠。

新增 RhProbeWork 跟踪检查／诊断所属探测的实际函数退出。未开始的任务取消后立即释放自身记录；已经开始的任务在 finally 才释放。父任务返回后若仍有探测在执行，保留归属，界面显示“等待 N 个地址探测结束”；最后一个退出后在原执行队列自动继续清理，无须再点重试。没有增加固定等待或轮询定时器。普通串流连接的选路没有接入这个跟踪器，仍走原入口。

配置或固定证书变化后，旧检查现在明确显示“需重新检查”和“连接配置已更改，请重新检查”。过期对象不携带旧 outcome，不宣称在线或已认证；已保存证书仍保留，后续实际连接继续严格检查。不删除配置、不把旧结果当作新地址的检查结果。

宽设置页完成后的侧栏原本已由布局刷新正确更新。本轮补验确认草稿、正在编辑的 EditText 和焦点保持，**没有将它列成已复现的产品缺陷，也没有为此添加重复刷新**。

## 耗时对照

比较不可变的 preview.152 模拟器主 APK 与本轮 preview.153。使用同一个兼容测试类，只调用两版共同接口；每版三个新进程，每轮 25 次完整主动检查，每次严格为一次自有回环 HTTP。每轮仅清理本轮独立包数据，配置均为 1 设备、1 配置、951 字节；日志记录实际包版本、进程 PID 和安装 APK 摘要。没有重新构建旧主 APK。

第二轮反转版本顺序。小样本未出现一致增加的延迟，也不能据此宣称首次检查提速。最初未统一配置的六轮保留在 `latency-*-trial*`：152 有 1 台设备／配置，153 有 5 台，后续读取和规范化量不同，不能将约 3 ms 的差距归因于跟踪器。正式对照为 `matched-latency-*`，汇总见 `latency-comparison153.json`。

这测量的是单线路完整检查，包含其检查调用和主线程派发，**不是串流首帧、画面帧率或真实外网性能**。冷进程的类加载等开销仍在数字中，没有把它们删掉。

## 剩余范围

受控不响应中断的子任务只证明真实函数寿命的归属与 UI 行为，不是系统 DNS 或运营商网络实测；仍需测系统解析退出及最坏等待。实际多线路、打洞／中继、后台发现的来源分类、真实 WebDAV 在检查期间改配置、OPPO 和最终交付继续保留。宽设置页与直接写入共享配置的验证不代替真实 WebDAV 传输。

Windows 本地候选仍为 preview.151；日常 Windows preview.101、模拟器正常 Android preview.129 及八份保护文件未改。完整 UI 目标保持进行中。
