# Windows 悬浮键盘失败反馈与重试

本地候选 preview.95；日常便携版仍为已交付的 preview.93。本轮不操作 OPPO，也不将新增反馈等同于旧首次显示失败的根因已经解决。

## 已确定的问题与改动

原 `floating_keyboard::follow` 的错误仅留在工具栏诊断字段，操作页不显示；同一来源几何的失败可以被缓存，而再次 `enabled:true` 不会生成新的尝试。修改生产代码前，两条新增 Core 回归分别复现“失败未展开提示”和“重试没有新请求”；日志为 `feedback-baseline.log`，另两条相关测试通过。

- 显示失败展开“操作”页，提示未显示、窗口过小或远程窗口暂不可用；保留独立的远程操作反馈。
- “关闭悬浮键盘”和“重试”均使用已有 `stream.keyboard.floating.set`，分别传 false／true。每次 true 产生新的运行期请求号。
- 同会话、同请求的反馈才可更新提示；旧失败不能污染新连接，旧成功不能清除新失败。用户收起后，同一错误不会不断展开面板；原位置的控制开关保留提示标记。
- 已确认首帧的活动会话连续两秒缺少可用窗口才给等待提示；主动最小化、展开面板、弹出菜单、连接恢复不启动该等待。
- 统计 `floating_keyboard_state` 只记录状态变化和列举的原因码，不写原始错误、参数或令牌。用于后续补齐旧样本缺少的 UI 状态证据。
- 操作区给滚动条单独留白，避免覆盖右侧按钮。

真实失败由本应用的隔离 `view.ui.native-window` 调整自有原生窗口尺寸触发，未注入伪造错误。窗口小于按键布局要求时提示出现；用户收起后重复读取不强行展开；还原原始尺寸、按“重试”产生新请求并恢复实际键盘。主机显示器、源端分辨率和串流进程均未重建。

`after-dark01` 和 `after-light01` 的反馈／重试子流程通过，之后在第一轮附加最小化／恢复时均检测到前台激活。第二轮移除 QA finally 中多余的同尺寸 resize 后仍复现，故不能把它归因于这一条冗余命令；也未证实是新增生产反馈代码造成。两份失败、前后窗口状态及恢复后的新 render_return 均保留；此前 preview.94 未经该缩小／放大前置步骤的基本恢复结果仍保留原范围。下一步定位恢复激活的实际调用者，保持日常 preview.93。

一次早期 UI 测试把缩放事件后的逻辑尺寸交给固定 1 倍的测试适配器，实际输出仅 355×292 像素，导致 225% 下视口过小。已改用明确物理尺寸，并断言输出像素尺寸；失败日志和图片仍保留。此项是测试设置修正，不作为生产环境的 DPI 故障修复。
