## 原因和修正

原 devices.refresh 在平台探测返回后整体替换当前列表。平台工作期间 Controller 允许其他 API 和后台任务推进，因此刷新读到的旧列表可能晚于新的配对结果到达。旧实现明确复现：连接页已经显示配对完成，设备行却又变为未配对；另一轮移除的设备被重新加入，新增设备消失。

新增 [device_refresh.rs](../client/crates/rhremote-core/src/device_refresh.rs)，沿用现有动作和探测执行顺序：

- 探测前保存列表及连接／配对代次；相关操作已推进时，忽略这次过期观察，不以旧结果修改新身份状态。
- 对仍属于同一代次的返回，只更新从请求开始到现在没有改变的记录。保留期间的移除、新增和修改，再应用当前 Saved 中的别名和排序。
- 设备列表就地显示“刷新中…”并临时禁用刷新按钮；并发到达 Controller 的重复请求合并为 pending，不再启动第二个探测。串行队列内已经排队的重复点击仍不在此保证范围内。
- 失败保留列表、当前设备与搜索，重新启用刷新；错误留在对应列表，重试成功后清除。两个运行状态字段不进入 Saved 或 WebDAV 共享配置。

137 还修正了生产队列的错误旁路。136 的控件检查没有经过该旁路：原工作线程会将同一刷新错误再写到全局 status，重试清掉局部错误后，全局提示仍可能残留。把原逻辑提取为同一 report_queued_error 并接入回归后，旧逻辑明确失败；137 只让刷新使用自己的局部错误通道，其他排队动作保留原处理。

UI 按钮、Controller 和接口仍使用 devices.refresh，没有新增另一套“成功”或“重试”动作，也没有放宽配对／证书校验。

## 接口状态

GET /v1/state 新增 devicesRefreshing 和 devicesRefreshError。它们分别表示当前实际探测工作及其错误；界面控件使用同一状态。

已有刷新进行时，重复 devices.refresh 返回 result.skipped=true、result.refreshing=true，原工作继续。有效工作完成后 refreshing=false；如果连接／配对代次已经变化，result.stale=true 表示观察没有覆盖当前设备状态。读取该动作的成功回执，不能替代等待原 pending 工作完成。

## 验证

最终完整回归 `full-rust137-final.log`：Core **141**、UI **253** 项通过，零失败，另 **4** 项既有专项用例忽略。

五个 Core 用例覆盖配对期间的过期结果、移除／新增、地址编辑、失败后重试，以及并发请求合并。最初四个用例在旧实现失败；地址修改保护随后补齐。测试使用可暂停的平台边界，先确认工作确实仍被暂停，再推进新的状态并释放旧返回，不依赖睡眠假定竞争发生。

实际 Slint／Controller 用例包含生产队列的同一错误处理函数：两种主题、1180×780 和 720×560 两种窗口分别检查刷新中、失败、跨页返回、重试和状态还原，共 **12 张软件控件自身绘制图**。这些用例中的两台设备和超时是测试边界，不能当作日常三台设备或真实主机失败。

最终 Portable 另在实体 `C3273IUY / DISPLAY2` 完成浅深主题 × 设备页／连接设置页四组，**56 个检查点**通过，见 `native137-verification.json`。它从日常三台设备配置创建副本，保留别名、地址、其他客户端参数和排序，不复制原生配对身份或 WebDAV 凭据。实际刷新之后，把设备行动作排在同一生产队列中，等待选择确实改变，再核对刷新完成；不是只看控件请求已分发。四张窗口图均由应用自身绘制，没有激活窗口或注入系统输入。

## 尚未解决的等待

本轮没有改变以下执行路径，也没有据此声称连接等待已经缩短：

1. [启动顺序](../client/crates/rhremote-ui/src/lib.rs) 会先执行整组 devices.restore 探测，再创建 UI 和本地接口。窗口出现前有一条明确的网络等待路径，实际占比尚待逐设备计时。
2. 手动刷新在同一动作队列执行；后续连接等动作仍可能等待探测结束。Native.probe 与会话共用 Network／中继资源，不能直接多开线程改变通道所有权。
3. Native.probe 当前使用默认 Profile；刷新状态与各设备实际连接策略的对应仍需补齐。

下一步需将本地设备恢复、可取消的状态探测、配对准备和会话通道归属一起处理，并把窗口前的启动阶段及时落盘；现在的启动 mark 在连接录制开始前主要保留于内存。独立验证窗口何时出现、按钮何时响应和后继连接何时收到首帧，不能混成一个耗时。

claw／本机旧 Sunshine 重复证书的 401 是另一个部署问题，服务更新仍待此前确认；这次 UI 状态修正没有替代服务更新或真实配对验收。
