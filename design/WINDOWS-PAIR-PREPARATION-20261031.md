# Windows 配对准备与取消

2026-10-31，客户端候选 `0.2.11-preview.142`。本轮从 141 继续修改 Windows 配对，日常客户端仍是 101，Android 仍是 129；没有安装、提交或公开发布本候选。

## 问题与改动

原来 Core 点击配对后立即公开 PIN 并显示“等待主机确认”，Native 随后在配对／进程锁内同步选择线路。动作队列需要等 `device.pair` 返回才能处理取消；网络慢时，页面描述与实际阶段不符。配对结束后还会再运行一次在线探测，即使 PIN 交换已经成功也要等待。

现在配对有三个阶段：

| 阶段 | 页面 | PIN |
| --- | --- | --- |
| preparing | 正在准备配对连接 | 隐藏 |
| contacting | 正在联系主机 | 隐藏 |
| pairing | 等待主机确认配对 | 显示 |

线路选择和进程创建在独立 worker 中完成，使用已有可取消线路解析。等待设备探测释放通道时也可取消，取消不再等待同一个前台租约。准备任务与原生配对进程归同一次配对所有，独立于串流进程槽位；迟到的取消请求找不到自己的配对时，不结束任何串流。

Core 只接受相同 `pairAttemptId` 的阶段信息，阶段不倒退；准备中只保存内部 PIN，不通过公开状态／UI 暴露。Native 原子写入且经格式和本次编号校验的签名取消凭证，表示已经开始 PIN 协议，此时才显示 PIN。**这不是服务端已接收请求或已接受 PIN 的证明**；成功仍要求本次原生进程退出成功且结果为 `paired`。结束后使用该协议结果，不额外发起在线探测，也不会把缓存中的 `paired=true` 当成本次配对成功。

取消立即被接收，页面继续等待自己的 worker、进程和取消请求清理完成。签名取消请求完成后才释放旧通道，清理队列仍阻止立即复用未释放的资源；没有缩短既有中继线程退出预算或跳过清理确认。关闭应用先发出取消信号，前台租约等待移到清理协调任务中。
