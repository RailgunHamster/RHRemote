# Android 隐藏诊断栏的主线程读取

2026-10-31，记录 162。根据[实际 claw 会话的 UI 栈](ANDROID-CLAW-CURRENT-SESSION-20261031.md)，修正 `RhHome.refreshDiagnosticBanner` 在不可见时仍读取、解析完整共享配置的问题。产品改动仅在此方法；保留当前取消动作和设备连接阻止状态的刷新，显示状态栏时才读取最新设备别名，没有增加全局配置缓存。

## 对照与交互

使用独立包 `com.rhremote.client.uicheck162`、专用 emulator-5580；修正前后均标识 preview.162 / 380，修正前的 RhHome 与已核对的候选 158 字节一致。新增原生检查以 StrictMode 记录真实主线程文件 I/O，反射仅用于调用已有的私有刷新方法；诊断通过自己的 loopback HTTP 服务和实际取消按钮运行，不连接远端业务主机。

| 观察范围 | 修正前 | 修正后 |
| --- | --- | --- |
| 空闲、连接设置空闲、当前页诊断运行、取消后隐藏，各两组 | 8 次刷新均有配置 I/O，每次 7 条读操作违规 | 8 次均为 0 |
| 其他页显示诊断栏、显示期间改名，各两组 | 读取当前别名 | 读取当前别名，4 次检查通过 |
| 显式读取配置的正向对照，两组 | 检出 I/O | 检出 I/O |

7 条是同一次配置读取中的文件访问／打开／读取等 StrictMode 事件，不是读了七次完整配置。隐藏／显示期间的别名修改都能反映到状态栏；实际取消按钮关闭自己的 HTTP socket，完成后隐藏状态栏并禁用旧取消操作。

首次检测器过早恢复线程策略，正向对照也未收到回调，故该轮不计作有效证据。依据 [AOSP StrictMode 实现](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/core/java/android/os/StrictMode.java)，将监听保持到主线程消息处理完成；没有削弱正向对照和隐藏状态零读取断言。修正后的相同检测器在旧产品代码失败，在新代码通过，两份原始失败均保留。
