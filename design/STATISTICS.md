# 测试统计

Windows 与 Android 的测试模式每次连接自动创建 `rhremote.statistics/v1` 目录。设置 → 关于和 `statistics.configure {enabled: true|false}` 共用操作；`statistics.state` 返回模式和最近记录目录。模式仅属于当前安装，不参与 WebDAV 同步。Windows `start-rust-client.ps1 -TestMode` / `-ApiOnlyInputTest` 启用；两端功能测试也自动启用。

每次保存实际连接配置、单调时钟的 UTC 锚点、连接阶段和按帧号关联的 JSONL：首个视频包、组帧完成、解码提交/返回、解码输出、渲染排队结束、渲染提交/返回、明确丢帧及原因。Windows 组帧时间由上游毫秒时钟换算，精度不是微秒。Android 额外通过只读 JNI 读取上游微秒时钟，并记录 MediaCodec 回调到达与框架报告的呈现时间。

Windows 的 render_return 只表示 CPU 渲染/Present 提交返回，不代表屏幕完成扫描。Android 框架报告的时间可早于提交（例如按 Choreographer 的请求时间呈现），回调到达时间另记，不能把二者混用为正的显示延迟。丢失帧号无法单独定位丢失于网络还是主机。协议主机处理耗时是总值；没有服务器逐帧捕获/编码细分埋点时，不编造该细分。

高频线程仅入有界队列，后台线程落盘；队列最多 65,536 条、单文件最多 512 MiB，结束写 trace_end 和丢记录计数。报告明确标出记录丢失或缺少结束标记。只记录时间、帧号、大小、配置与状态，不存像素、音频、键盘文本、URL 参数、配对密钥或令牌。

`tools/collect-statistics.ps1 -Platform windows|android` 导出并分析最新测试。OPPO 用 app-private run-as 导出，不读取应用令牌到结果。主机只读日志在结束后采集，用 SSH 往返时间估计时钟偏移和误差范围；主机自身阶段耗时不依赖跨机时钟对齐。主机日志中的 Creating encoder → Streaming bitrate 区间仅是这两个标记之间的时间，后者位于 avcodec_open2 之前，不能声称是完整编码器打开耗时。

输出 summary.json、frames.csv、Chrome Trace Event 格式 timeline.json 与独立 report.html。HTML 时间线支持缩放、平移、按帧号定位与事件详情，并给出平均/P95/P99/最大耗时和逐帧间隔。原始 JSONL 分析成功后删除；下次测试删除已分析的旧目录，只保留当前仍用于排查的结果。`--keep-raw` 为明确仍需要的对照创建 keep 标记，使用完必须清理。未结束/损坏记录先保留以便诊断，不悄悄当作完整统计。

时间轴和默认视区以当前 connect_action 为 0，明确标记首帧终点。分段表显示累计起止时间及本段耗时，合计与首帧指标一致；程序启动与连接前空闲不计入本次连接。原始 HTTP/初始化调用可能并行或嵌套，置于可展开明细，不能直接相加。已分析的报告可用 `analyze-statistics.py <目录> --refresh-report` 从报告内的事件刷新展示，不重新采集或恢复已删除的原始记录。

Windows 的连接起点现在取按钮回调入队时间；直接 API 调用取分发器接收时间。新增 `connect_request_received`（来源及 UI 队列等待）和 `native_spawn_begin`，报告将操作排队和请求处理单列，避免把按钮等待排除在首帧耗时之外。请求立即进入 connecting 状态，启动中的旧轮询结果不能清除它或放行重复连接。

2026-10-21 实测：Windows 1920×1080/30/HEVC，去掉桌面鼠标模式的 3.5 秒提示等待和 RHRemote 连接前 1.5 秒等待后，连接至首帧渲染提交返回从 16.397 秒降到 9.817 秒；这是后续连接对照，不是冷启动或稳定帧率验收。之后仍有约 6.4 秒等待主机首包。Sunshine 重启后首连曾用 36.949 秒重测编码能力，需继续定位主机初始化；不能把该耗时归咎于 UI。

OPPO 实测记录 206 帧、零统计丢记录，连接至系统呈现回调到达 6.552 秒。独立的 winserver 控制台 FFmpeg 合成视频测试中，H.264 / HEVC 均成功编码 60 帧，但开始出帧前等待约 7.2 / 8.2 秒；该路径不使用 RHRemote、Moonlight 或桌面捕获，支持将剩余启动等待继续定位到主机 QSV 初始化。另两次设备/帧上下文实验失败，不把它们的时间当作有效编码性能结论。
# Sunshine 服务端诊断构建

服务端源码现维护于 `server/sunshine`，官方基准记录在 `server/UPSTREAM.json`。此前验证的优化和 `RHREMOTE_PHASE` 计时已经作为独立提交保留；正式构建直接编译维护源码。`tools/prepare-sunshine.py` 仅保留作固定官方基准的历史 A/B 对照，不用于覆盖维护源码。服务端单调时钟测量编码器探测、格式验证、采集重建、DDA 设备与 duplication 创建、编码器创建和首帧编码；不记录像素或声音。

`collect-statistics.ps1 -Platform windows -RunId <已结束的统计编号>` 可分析自动恢复之前的特定会话。服务端原生计时进入同一 timeline，服务端阶段耗时由单调时钟直接取得，跨机器对齐仍附带 SSH 估计误差。模拟中断结果和实际 Windows 解锁验收分别记录。

统一服务的 `service-events.log` 记录服务启动/退出和 Sunshine 子进程启动/退出。主机证据另附 SCM 状态及 PID，以区分 Windows 服务启动、子进程恢复和客户端连接；采集生命周期日志时去掉 PowerShell 文件提供程序的附加元数据。2026-10-22 统一服务已在 winserver 替换原服务并通过完整构建：停止 0.327 秒，重启就绪 7.806 秒，子进程异常后 1.190 秒重新拉起。它们不计作客户端首帧延迟。

此次 1080P30/H.264 首连（服务已就绪）为 10.702 秒，之后为 6.057、6.128 秒；后两次请求响应约 31 毫秒。后续一次的分段为连接/选屏准备 3.053 秒、握手 0.122 秒、首包等待 2.921 秒、解码及渲染 0.032 秒。首轮的选屏准备和 DDA 设备初始化更慢，保留独立阶段证据，不把延迟波动直接归咎于 Moonlight 解码。报告仍以 CPU render_return 为终点。对应三轮原始逐帧数据分析后清理，分析报告及当前对照需要的主机证据保留。

2026-10-22 服务端对照：同一 Sunshine 提交、1080p30/H.264/25 Mbps、客户端关闭声音。行为对照版后续连接首帧 9.291 秒，其中服务端编码器重探 3.307 秒、8 次 display_reset；优化版两次普通连接为 7.804 / 8.072 秒，连接期间重探约 6.9 毫秒，没有重复 display_reset。服务启动时首次能力验证仍存在，不能把缓存命中视为冷启动只用 7 毫秒。

优化版 8.072 秒连接的额外埋点：客户端 Session 初始化 644 毫秒、输入初始化 216 毫秒、自有 RHRemoteHost 选屏准备 2697 毫秒、协议握手 121 毫秒、等待首包 1882 毫秒、解码 31 毫秒。其余时间仍包括发现主机和获取应用等准备；嵌套范围不重复相加。剩余延迟也包含 RHRemote 自有代码，不能全归因于 Moonlight 或 Sunshine。

模拟中断的全程恢复：原始服务端约 14.772 秒，服务端优化后约 10.889 秒，修正本地状态查询连接超时及协议资源交接后 8.072 秒。ureq 的连接超时优先于总请求超时，本地查询现在显式设置 100 毫秒连接超时。只有原会话已成功出帧才启用有次数与时间上限的恢复；用户主动断开和受保护内容不进入恢复。

实际 Windows 锁屏/密码解锁单独验收：第一次发生串流中断，服务端进程重建并重探约 12.788 秒，自动恢复约 35 秒。最后一次先由 Windows 锁屏接口执行、WTS 状态确认已锁定，再由用户输入密码解锁；客户端和 Sunshine 进程均保持不变，无新连接，服务端采集重建约 910 毫秒，解锁附近最大的客户端 render_return 间隔为 3232.921 毫秒。此结果仅代表该次真实解锁，不能宣称所有解锁情形均不再断开，也不能代替稳定帧率验收。

## 后续启动优化（2026-10-22）

Windows 串流适配器现在仅轮询所选 Sunshine UUID，保留本次进程的成功认证应用列表校验；不再等待与该连接无关的主机发现和外部兼容性查询。Rust 主界面负责进度与错误，串流进程改用轻量窗口入口，省去重复的 Material 控件树和 GUI 手柄导航初始化；实际串流的输入处理仍由原生引擎初始化。新增 `client_host_found`、`client_apps_fresh`、`client_qml_load` 埋点，观察到开始 HTTP 查询由连接后约 1.8 秒提前到约 0.2 秒。

RHRemoteHost 枚举捕获顺序时先枚举已附着输出，不给无输出的显卡创建设备；仍逐个验证实际输出的 DDA 捕获能力。winserver 控制台相同输出顺序的独立对照为 3170 → 1204 毫秒；实际连接选屏准备由此前约 2697 毫秒降到约 1654～1714 毫秒。显示配置 C# 在构建时预编译为 Windows PowerShell 5.1 可加载的程序集，源码与程序集 SHA256 同时匹配才加载，缺失、过期或不兼容时保留源码编译回退。这个预编译的独立收益有限，不把全部收益归给它。
