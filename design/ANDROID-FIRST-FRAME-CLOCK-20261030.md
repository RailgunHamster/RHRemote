# Android 首帧计时的阶段边界

Windows 实际会话之后，继续运行未修改的 Android preview.122 完整会话并记录同期主机／模拟器负载。此轮在首帧之前失败，没有执行到 IME：`ui-session-full122-review-20261030/full122-light02`。配置、同步备份、字号、尺寸和密度均还原，应用已退出。同期 55 个负载样本见 `ui-session-load122-review-20261030`；不能据总 CPU 平均值判定某个业务程序或具体线程造成卡顿。

## 已确认的时序错误

同一份统计中的实际事件相对于 `native_attempt`：

| 事件 | 相对时间 |
| --- | ---: |
| Game 创建并登记本次 native attempt | 0 ms |
| 应用发起“首帧等待超时”的恢复 | 15115.517 ms |
| native `connectionStarted` / `connection_ready` | 24022.532 ms |

`RhRecovery` 原来在构造时启动局域网 15 秒、其他路径 30 秒的首帧 watchdog。Game 会早于 HTTP／RTSP／控制通道协商完成而存在，因此它会将尚在协商的连接当作没有解码出画面，并在原连接仍初始化时进入清理。此轮最终出现“上一会话清理超时”，不把它归为网络不可达或 IME 故障。

源文件和修正证据在 `D:\RHRemoteTools\ui-first-frame-clock126-review-20261030`。新增的“协商不能消耗视频等待期限”行为测试在旧代码实际失败。preview.126 将现有首帧 watchdog 移到真正的 native `connectionStarted` 回调之后：

- 原来的 15／30 秒视频观察期限不变，原生 HTTP／RTSP／视频通道超时和取消清理规则不变。
- 重复连接回调不会延长期限；取消、完成、已进入恢复或已交接的旧连接不能重新启动 watchdog。
- 早于该回调到达的真实帧保持有效，不会再次取得视频等待期限。
- 新增 `first_frame_wait_begin` 统计事件，记录预算和 attempt ID，不记录输入内容或凭据。

初始化阶段仍依靠原有原生阶段的超时及用户取消。此改动不证明所有驱动调用都能及时返回，也没有解决已经存在的清理长尾；这些范围继续保留。

preview.126 的完整 **476** 项 JVM 回归通过，零失败、零忽略；新构建与原 preview.122 的全部 native `.so` 逐字节一致。只更新专用 emulator-5580，安装前后十五份配置／身份文件哈希一致，没有操作 OPPO 或公开发布。

实际 `full126-light01` 中，`connection_ready` 为 9734.531 ms，`first_frame_wait_begin` 为 9734.557 ms，期限为 15000 ms；取得解码画面后没有触发媒体超时，首帧状态观察为 15698 ms。它不是同负载性能对照，不据此宣布启动速度改善。
