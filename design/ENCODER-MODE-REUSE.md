# 软件编码器的模式变化复用

2026-10-23，已在 winserver / claw 部署 `f517c155`。winserver 分辨率变化后的编码能力检查从对照中的 2206 / 3009 ms 降到约 12–17 ms，日志确认使用了经过检查的模式变化复用。显示准备中的 D3D 开销仍有明显波动，启动优化继续进行。

仅在已经成功选择、且服务端明确配置 `encoder=software` 时启用新判断。自动选择和硬件编码器保持原有 DXGI 失效策略；实际捕获输出、捕获设备、会话编码器和首帧仍正常创建、校验，不缓存旧输出索引。

每次判断重新创建 DXGI factory，并连续两次读取一致的元数据。相等性直接比较原始字段序列，未用摘要替代身份校验：

- 显卡完整 LUID、PCI 标识、驱动版本查询结果、适配器和输出顺序。
- GDI 输出及真实显示设备路径、源和目标编号、输入桌面、是否附着。
- 位置、旋转、缩放、刷新率、像素格式、位深、色彩空间、HDR 状态及显示色度/亮度。
- 软件编码器选项、配置的捕获/显卡/输出、HEVC/AV1 模式和视频头策略。

只有像素宽高允许变化；其余任一字段变化、查询失败、库存不完整或两次读数不一致，都要求完整探测。旧 factory 失效但宽高未变也要求完整探测，避免把无法解释的变化认作模式变化。

为排除显卡重置，保留真实成功创建的首个 D3D 设备引用，只用于 `GetDeviceRemovedReason`，不用于捕获或编码。新设备不能掩盖旧设备已经丢失；缺少健康依据不允许模式变化复用。每张活动显卡至多一个引用，最多 64 个，停用显卡的引用按新库存释放。它可能延长原设备及关联资源的存活，需在部署验收中核对内存及会话清理；不能声称没有资源开销。

元数据使用临时的调用线程 Per-Monitor V2 DPI 上下文，退出时恢复，不改变进程、显示器或用户缩放设置。实测诊断程序不设置此上下文时曾把 2520×1680 读成 1120×747；修正后按物理像素读取。该差异不能被当成真实分辨率变化。

本地 MSYS2 UCRT64 编译：6 组故障/所有权用例通过，并将同一组加入完整 GoogleTest 和 CI。覆盖冷状态、缺失信息、竖屏/4K尺寸、不明失效、硬件路径排除、原设备丢失、字段/适配器变化、引用替换和 64 项容量边界。Windows 元数据头文件也通过独立严格编译；winserver 原服务上连续 2520×1680 → 1080p → 不变 → 恢复的只读查询稳定，元数据摘要一致。真正的逐字段复用决策仍以部署后的引擎记录为准。

对照基线使用旧引擎 `7332952e`、新 Rust 主机 `2051377`，同一 Windows 客户端 `128cc268`、LAN、静音、H.264、请求 30 FPS / 5 Mbps：三个用例首帧为 6572.356、2549.520、7166.155 ms。证据 `D:\RHRemoteTools\encoder-env-short-20261023.json`；配置、同步、选中设备和原有虚拟屏模式已恢复。OPPO 未操作。

API 语义依据：[IsCurrent](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgifactory1-iscurrent)、[CheckInterfaceSupport](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiadapter-checkinterfacesupport)。驱动版本查询不用于推断 D3D11 接口支持；查询不支持时保留其结果，并仍要求旧真实设备健康及其他完整元数据相同。
