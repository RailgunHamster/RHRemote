# 自动码率与指定窗口串流

2026-10-31 用户追加要求：码率提供 Auto，改善外网卡顿；增加只远程选定窗口的模式，减少无关画面与流量。两项均未完成，不以现有固定外网码率上限或桌面裁剪冒充。

第一阶段已接通双端配置和连接时起始预算，通过本地回归，尚未发布；持续自适应及窗口捕获仍待实现。[第一阶段证据与限制](AUTO-BITRATE-STARTING-RATE-20261031.md)

## 用户流程

每台设备的连接设置增加“自动码率／手动码率”。原手动值保留，旧配置继续使用原值；自动模式显示当前生效码率和调整原因。自动选择属于该客户端与该设备的配置，遵守现有跨端参数隔离与 WebDAV 规则。

连接模式提供“桌面／指定窗口”。选择窗口后列出远端应用和窗口标题，连接页与控制面板都可以重新选窗口。窗口关闭、最小化或不可捕获时显示对应状态并保留选择入口，不自动改成整个桌面。窗口模式的输出应按窗口比例与像素需求编码，仍支持自动码率。

## 自动码率实施顺序

1. 确认两端、Sunshine 和编码器的实际调节接口。当前检查发现 Moonlight 配置只暴露连接时 bitrate，RHRemote 的 remoteBitrateMbps 也只是固定外网上限；不能将它描述成运行中的自适应。
2. 增加可选配置与共享动作，两端保存／取消／离开保护、复制与同步完整接入。自动与手动切换不覆盖手动值。
3. 根据实际选中线路及画面规格给出保守起始值；链路反馈必须来自实际网络丢帧、接收队列、RTT／抖动等，不把解码或服务端负载造成的掉帧直接算成网络拥塞。
4. 协商服务端动态调节能力，再在支持的编码器上实现会话内调节与回执。没有能力的旧服务端只能采用连接时估计，并如实显示该限制。正常运行不通过频繁重连来调码率。
5. 降码率快、回升慢，设上下限、滞回和冷却时间；保存调整前后值、输入统计与效果，用同一动态源核对实际流量和画面停顿。验收基线仍是 1080p30，不恢复 60 帧／4K 目标。

## 窗口模式实施顺序

1. 复用服务端已有 Windows Graphics Capture 路径。Microsoft 的 CreateForWindow 可以直接创建单 HWND 捕获项，最低 Windows 10 1903；现有 wgc_capture_t 已处理帧池、D3D 纹理和硬件编码路径，无须另做客户端截图方案。
2. 主机枚举与选择窗口均提供已认证接口。返回会话内不透明标识，校验 HWND、进程与创建时间，避免关闭后句柄复用指向其他应用；不将原始句柄作为长期同步配置。
3. 从选定窗口生成捕获纹理并接入原硬件编码，处理窗口尺寸、DPI、纵横比与帧池重建。比较窗口原生像素与输出上限，避免重新放大到整个 4K 桌面而抵消节省。
4. 实现内容区域到主机窗口的输入坐标映射，补齐弹窗／菜单、焦点、窗口移动与缩放。窗口捕获不等于独立 Windows 会话，输入仍可能使主机上的应用获得焦点，不能承诺与本地输入互不影响。
5. 对自身测试应用验证被遮挡、最小化、关闭、尺寸变化及所属弹窗，证明没有带出其他桌面内容，再接入两端正常连接与恢复。

### 2026-10-31 代码核对：仍需改变的链路

- `display_wgc.cpp::wgc_capture_t::init` 当前调用 `CreateForMonitor`，帧池尺寸取 `item.Size()`。可扩展为 `CreateForWindow`，但不是仅替换这一行：`display_wgc_vram_t::snapshot` 仍将纹理大小与显示器 `width_before_rotation/height_before_rotation` 比较，不同就返回 `capture_e::reinit`；按现状直接传入小窗口会不断重建。
- `display_vram_t::alloc_img` 也按显示器大小分配纹理；必须让源尺寸来自窗口捕获项，处理 `ContentSize` 与帧池 `Recreate`，复制有效内容区域，避免缩小后的未定义边缘进入编码器。输出协商需与客户端实际解码尺寸相符，保持比例且不将小窗口重新放大为桌面尺寸。
- `video.cpp::make_port` 和 `input.cpp` 的绝对坐标按显示器源尺寸、偏移和桌面环境计算。窗口移动、跨屏或 DPI 改变后，需同步更新映射；点击黑边不注入窗口外，旧帧对应的坐标不能打到新位置。
- 当前检查只证明已有 GPU 帧池／纹理链路可复用，没有启用新的窗口捕获入口，也没有改变任何主机正在运行的服务。

用户入口维持简洁：连接设置选择“桌面／指定窗口”，后者先列出应用名与窗口标题；会话控制中提供“切换窗口”。每次从主机重新解析目标，不将 HWND 同步到其他客户端。对话框和菜单必须单独验证，不能声称捕获主窗口就自动包括其所有所属窗口。最小化可能停止产生新帧，应显示暂停原因，不能继续把最后一帧当作可交互的新画面。

源模式应独立于现有 `windowMode`（客户端窗口化／无边框／全屏）和 `displayMode`（桌面源的自动屏幕／虚拟屏），避免共用“窗口”一词却修改另一项配置。窗口源不为匹配平板而改变物理显示器模式；客户端已有的缩放和横竖屏负责本地布局，输出保持窗口纵横比。选择源模式可存入本客户端的每设备参数，实际窗口目标由已认证会话重新选择，不同步临时窗口句柄或把当前窗口标题变成长久定位凭据。

首版只改变画面源，现有声音开关继续控制音频；不能把系统音频描述成“只捕获所选应用声音”。服务端不支持窗口捕获时明确显示需要升级，不能静默把选定窗口请求降成完整桌面。

## 如何证明省流量

传输字节由实际码率决定，不单由裁剪面积决定。仅视频按固定 25 Mbps 约为 11.25 GB／小时，4 Mbps 约 1.8 GB／小时，另有音频和协议开销。窗口内容更少可降低维持清晰度所需码率，但不能事先承诺节省百分比。

静止的桌面背景通常已能被帧间编码压缩，因此不能用“窗口占屏幕四分之一”推导“流量下降四分之三”；如果选定窗口仍播放高动态视频，它仍可能需要较高码率。收益按实际发送／接收字节对照，而非配置值推算。

保持应用内容、动态程度、编码、帧率和网络条件相同，对照完整桌面／窗口、手动／自动四种组合，记录实际发送及接收字节、丢帧、排队与可读性。先用独立测试窗口和专用模拟器；OPPO 未恢复测试，正在使用的客户端和服务不为本功能验收而中断。
