# Android 界面配置读取与实际连接复验

preview.122 修正设备列表和状态查询在一次操作内反复读取整份配置的问题。旧版实测中，恢复前台的主线程连续解析、规范化和校验配置，心跳最长迟到 15.654 秒，添加设备的完成结果无法及时显示。此次修改将主列表绘制、设备状态更新及状态 API 各自使用的配置统一为一次经过校验的读取。

证据目录：[ui-config-snapshot122-review-20261030](D:/RHRemoteTools/ui-config-snapshot122-review-20261030)。旧版失败和线程采样保留在 [natural121-ui02](D:/RHRemoteTools/ui-rtsp-current-review-20261030/natural121-ui02)。

## 原因与修改

旧路径由 `PcView.onResume → RhHome.resumed → syncChanged → renderDevices` 进入列表。排序、各行名称、地址、搜索摘要和选中设备配置分别调用 `RhShared.read`；状态 API 也为每台设备分别读取别名和配置。每次读取都会解析 JSON，再执行 `normalize/validate`，检查全部客户端的连接配置。现场配置只有约 11.5 KB、三台设备和四个客户端组，重复读取仍被放大为主线程长任务。

独立采样线程每 250 ms 向主线程提交一个心跳；超过 750 ms 时记录最多 30 层 Java 栈。旧样本 96 次迟到采样中可见 JSON 解析和 `RhShared.normalize/validate → RhProfile.fromClientJson`，并有少量锁等待。它证明这次“查找失败”包含客户端界面阻塞，不能用空的 RTSP 记录归因给服务器。

新路径把同一次读取返回的 `JSONObject` 传给排序、别名、地址和配置读取。状态响应内的别名、连接参数和已保存文档来自同一份提交，不再混合原子写入前后的内容。下一次操作重新读取；没有跨操作的全局配置缓存。`RhShared.read/normalize/validate`、写入、配对准入、证书验证及协议处理均未放宽。

## 回归与实际短测

新增三项读取一致性回归：在第一次读取后立即原子替换有效配置，确认同次显示和 API 响应保持一致、下一次操作能看到新值，以及后续非法 schema 仍失败。原版三项中两项失败，修复后全部通过；完整 JVM 套件 472 项通过。

## RTSP 证据边界

部署包、运行的服务端 EXE 和对应源码版本已对齐。部署 EXE 的反汇编确认 `WSASend` 后使用实际发送字节数累计并继续发送；客户端接收循环也累计实际接收长度。机器码只能说明执行路径，不能代替发生失败时的运行数据。

增加了仅保存 TCP 头元数据的有界采集工具：明确指定网卡和两端地址，只筛 TCP48010，snaplen 54，最长 300 秒，关闭混杂模式；不保存 RTSP 正文、密文或密钥。四项头部解析测试通过。

修复版两轮各捕获 68 个包，丢包计数均为零，记录了完整握手与正常关闭的序号／确认号／长度。两轮均未复现旧版 SETUP 的 expected=148／received=147 或 155／154，不能据此认定少字节问题已解决。此前查找阶段失败的空采集也继续保留。
