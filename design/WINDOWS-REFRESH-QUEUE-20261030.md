## 原因和实现

此前 [主窗口](../client/crates/rhremote-ui/src/lib.rs) 将手动 devices.refresh 与导航、设备选择、保存及连接放在同一个串行接收循环。NativePlatform 逐台探测，后来的本地操作必须等待整个刷新结束。给刷新加“刷新中”文字只能说明已有工作，不能让后续操作越过它。

提取同一个生产接收循环到 [action_queue.rs](../client/crates/rhremote-ui/src/action_queue.rs)，先保留旧行为复现，再将刷新放到后台。其 Controller、共享动作、错误通道和队列时钟保持一致；此前的并发合并和旧结果隔离仍在 [device_refresh.rs](../client/crates/rhremote-core/src/device_refresh.rs)。没有创建只用于测试的另一套派发逻辑，也没有把其他业务操作全部并发化。

刷新与会话原先共用 Network、transport.key 和同一个 TransportClient。只开后台线程会产生探测替换连接中继通道的竞争。本次新增 [device_probe.rs](../client/crates/rhremote-ui/src/device_probe.rs)：

- 空闲探测领取唯一租约；有前台工作或前台等待者时，不开始下一台探测。
- 前台请求先标记现有探测取消，并等待其租约释放，再取得会话／设备锁。没有持有这些锁等待探测，避免相反锁序。
- 探测检查现有的连接、清理和原生子进程状态；活动会话及待启动连接期间继续保留原观察。
- 路由查找、Tailscale 查询与 ping、原生 app-list 等待都检查同一个取消标记。取消只结束本次探测的子进程及其借用通道，返回原设备记录，不把取消误报为离线或未配对。
- 前台连接仍按原流程建立 Recovery 的 pending 归属；随后的列表探测会因 pending／活动子进程而跳过。

[平台适配](../client/crates/rhremote-ui/src/platform.rs) 中，devices.restore 现在默认只恢复 Controller 提供的本地列表及观察，不重新扫描网络；它同样先让旧探测清理。启动路径显式传 probe=true，保留原先窗口前的认证检查。该内部动作不在公开 Controller catalog 中；没有新增允许外部写入配对事实的 API。

138 未保留同步新记录的本机识别，最终复核时将其留为中间候选，不交付。`baseline-restore-self139.log` 明确失败：没有共享 isSelf 标记的本机行变为可连接。139 从已观察到的 localhost 服务 UUID 恢复本机标记；还没有缓存时，只查询一次有 700 ms 预算的本机 serverinfo，不重新探测远程设备。之后原列表探测的成功本机观察继续更新缓存。同步记录中的旧标记不能让另一台电脑继承本机身份。新增回归连到真实 NativePlatform／Controller，核对本机拒绝连接且仍能打开连接设置。

手动刷新使用 Controller 在开始时取得的每台设备有效配置，覆盖调用者提供的 profiles 参数；刷新期间某台已保存策略发生变化，不将旧策略的观察写回该台设备。其他未改变设备仍可更新。配对完成后的辅助检查也改用该次配对的有效配置。

## 回归和实际窗口

`baseline-queue-correct-page.log` 保留旧队列的失败：设备探测被软件门闩暂停，设置导航在 500 ms 检查预算内仍停在 devices。`fixed-queue01.log` 在同一测试中通过：设备探测仍挂起，导航已经完成。首次 `baseline-queue.log` 的目标页名曾误写为 app-settings，已更正为生产实际的 global-settings 并重新复现；首份不能作为有效页名断言的依据。

最终来源通过 Core **142**、UI **260** 项，另有 **4** 项既有忽略。证据为 `full-rust139.log`；138 的旧结果及未覆盖的本机导入失败一并保留，不是对全部真实网络或安装场景的完成声明。新增覆盖包括：

- 生产队列在暂停探测时继续处理导航。
- 真正 Slint 刷新、设置按钮与同一个生产队列，在暂停期间切页并保持设备、配置文件及状态。
- 前台请求先取消、等待探测清理，再复用通道；等待者阻止下一台探测；两个前台请求互斥。
- NativePlatform 的配对入口经过同一租约边界，未在旧探测退休前进入配对准备。

- 同步本机记录恢复本地标记，其他电脑不能继承该标记；本机连接拒绝与设置编辑分别验证。

## 保留的等待与范围

此候选没有解决窗口创建前的全量设备探测：启动仍显式使用 probe=true；其默认策略与手动刷新按每设备策略的差别仍待处理。不能将刷新队列通过写成“启动已加速”。

前台让探测退休也不等于零等待。尚有不可在中途打断的本机 serverinfo 请求预算 700 ms；TransportClient 的已有 worker 清理上限为 25 秒，相关取消可能经过这段清理。没有修改该上限、忽略清理或让新会话抢用尚未确认释放的身份；真实外网／中继的交接预算仍需测量。

配对本身的路由准备仍同步执行，取消准备期间的完整路径尚未解决；连接／保存各自的业务工作仍可能占用普通队列。这轮只证明刷新本身不再占住普通队列，不能扩大为“所有操作都不再等待”。

启动阶段的 mark 仍主要等到连接录制时才落盘；还需将本地设备载入、待检查状态、可取消探测与即时启动记录一起处理。界面出现、按钮响应、连接受理和首帧应分别计时。真实中继、活动会话、OPPO、旧 Sunshine 重复证书部署及完整 UI／交付验收继续按 [TODO](../TODO.md) 推进。
