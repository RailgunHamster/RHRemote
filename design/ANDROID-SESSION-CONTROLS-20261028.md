## 真实串流与远端结果

证据根目录为 `D:\RHRemoteTools\ui-android-session71-review-20261028`。最终主应用安装文件与保存的 `RHRemote-71-final-emulator.apk` SHA-256 一致，见 `installed-main-proof.json`。测试包新增显式启用的 `RhSessionRemoteInputProbe`；它通过实际 View 按钮及 ListView 菜单行回调操作正式动作，没有操作系统键鼠驱动客户端界面、ADB 端口转发或读取私有控制令牌。

测试使用专用 emulator-5580、既有配对身份及 winserver。为了核对 UI，连接临时使用 1080p30 请求、6 Mbps 和模拟器软件解码对照，声音关闭；这不代替默认 25 Mbps、默认解码器、OPPO、外网或动态帧率验收。

每条流程包含物理屏 → 既有虚拟屏 → 原物理屏、真实视频 Surface 读取、分组面板、返回／继续连接、主动断开，以及应用内 MotionEvent 双指放大至约 150%、静止手指保持比例和实际还原按钮。服务端对应日志尺寸变化为 1920×1080 → 2520×1680 → 1920×1080，每个样本只有一个自身主机逐帧记录标识。原始重复尺寸保留；尺寸相同的初始化或重建日志没有被当作另一轮切屏。

15 步远端验证针对独立 WinForms 测试窗口：

1. 通过正式触控动作激活属于该窗口的落点。
2. Ctrl+Alt+四方向、Ctrl+C / A / S / F，各收到一次。
3. 实际“窗口移到右屏 / 左屏”按钮，把该窗口移到 DISPLAY25，再移回 DISPLAY1。
4. 实际 Ctrl+Alt+Delete 按钮后，输入桌面不可访问、错误 5；实际快捷键菜单的 Escape 后恢复 Default。没有取得受保护桌面的名称或图像。
5. 再次确认并激活属于测试窗口的落点，实际 Alt+F4 菜单行关闭该窗口。

每次发键前均核对测试窗前台归属及修饰键释放。四个 Ctrl+Alt 方向键在该窗口前台期间注册，失焦或关闭时注销。远端核对结果通过本次专属证据目录和分步确认文件返回测试包；它们没有新增生产服务或网络监听端口。窗口移屏及 Alt+F4 只作用于这个测试窗口。

`session-remote-input.json`、`source-*.json`、`result.json`、`host-capture-proof.json` 分别保留客户端、远端和服务端证据。浅色解码视频图中可人工看到对应测试窗口标识；没有自动源像素匹配或物理显示呈现校验。

最终两条原生记录分别有 621 / 642 次解码输出、601 / 619 次渲染提交和对应 Surface 回调；各有正常 trace_end，lost_events=0、size_limit_reached=false。这些计数不代替持续 FPS 或端到端时延验收，跨机器时钟未用于计算按键延迟。

## 快捷键仍有未解决的偶发样本

`light06` 在 Ctrl+A 处失败：客户端返回已发送，远端窗口最终只记录到此前的 Ctrl+C，结束时修饰键为 0。该轮没有通过，`failure.json`、原生记录及服务端有界日志保留。这个样本还没有逐键 Windows 消息记录，因此暂不能区分没有送达、修饰键状态不对或应用消息处理差异。

随后 `light07` 的 Ctrl+A 同时出现 Win32 key-down / key-up 和带 Ctrl 的托管 key-down，完整流程通过；它不能解释前一失败样本。生产键盘发送及服务端实现未改。本轮确认客户端 checked JNI 的成功只代表输入队列接受，不能据此声称远端应用已执行。服务端日志区间没有对应 libvirtualhid 键盘提交错误，也不足以证明应用收到了该事件。

后续应在失败样本中同时取得客户端入队、主机注入和测试窗键消息的同次证据，再选择修复位置。此项保留在 TODO，没有把正向样本扩展为快捷键稳定性已解决。

## 观测工具修正与失败记录

- preview.69 的 light01 完成既有选屏及应用内双指缩放流程。light02 是 preview.71 首个候选，完成 15 步回执；它只包含设备名对齐，最终候选随后补齐缩放文字对齐。旧候选的源文件及哈希单独保留，没有用于证明最终画面。
- dark03 在等待 Ctrl+Alt+Down 时超时，远端该记录比前一事件晚约 35 秒。旧测试窗在 UI 线程做状态和事件文件 I/O；该轮没有充分证据指明具体阻塞调用，不能直接归为客户端输入延迟。
- 测试窗改为 UI 线程生成不可变快照、后台合并写入，并排队保存每个具名事件；停止命令的读取也在后台，写入不再强制逐次落盘。后台写入失败或不能结束时，结果为未确认，不将它计为成功。
- dark04 的可用状态／修饰键护栏中止，清理也没有确认结束。补发停止后确认窗口结束；驱动随后改为有界等待满足原护栏，并让停止命令不依赖先读到状态。原来各项前台、落点、按键和最终结果检查均保留。
- dark03、dark04、light06 都保持失败。两个早期窗口分别有 `source-stop-retry.json` 确认关闭；其余窗口正常结束，临时计划任务均删除。最终 source 工具还只记录固定测试虚拟键的有限消息、修饰键掩码及时间，不记录任意文字或全局输入；最终源码以 Windows PowerShell 5.1 编译检查通过。
