# tc 中继带宽与动态画面验证

2026-10-23。独立 HTTPS 中继仍为 33449；生产 443 未切换。本轮没有操作 OPPO、变更 tc 业务配置或启停业务服务。下面分别记录公网传输基线、DERP 合成数据和实际独立 QUIC 媒体，三者不能互相替代验收。

## 公网 TCP 对照

新增 tools/measure-ssh-throughput.py，使用现有 SSH 别名，关闭 SSH 压缩。只传递固定生成的数据，核对两端字节数和 SHA256，不读取用户文件、不新增监听或防火墙规则。默认每方向 16 MiB，单次有期限，超时只结束本次创建的 SSH 进程。

| 对照 | 数据量 | 实测速率 |
| --- | ---: | ---: |
| tc → 本机，单连接 | 16 MiB | 5.965 Mbps，传输 22.500 秒 |
| 本机 → tc，单连接 | 16 MiB | 81.840 Mbps，传输 1.640 秒 |
| tc → 本机，两条独立连接同时下载 | 每条 8 MiB | 合计 5.492 Mbps，含连接建立共 24.437 秒 |

单连接下载的逐秒数据在初始短突发后主要为 5.5–6.2 Mbps。双连接没有将总带宽翻倍；它们分别用时约 15.16 / 23.53 秒，不能把各自平均速率简单相加。相应远端 SSH 进程累计 CPU 约 0.05 / 0.08 秒，Python 生成与校验各约 0.012 秒，没有处理器满载证据。

这些证据表明当前 tc 到本机的公网方向存在约 6 Mbps 的共同吞吐限制；它在不使用 DERP、QUIC、Sunshine、解码或图形界面的对照中也存在。尚不能把它确定为云套餐标称带宽，仍可能涉及公网路径或其他共享限制。它不说明局域网能力只有 6 Mbps。

四项协议回归通过：下载完整性、上传按收到的内容计算哈希、提前结束不报告成功，以及拒绝参数注入和无界输入。GitHub 的 network-diagnostics.yml 在 Linux 持续执行这些测试；Windows 本机也已运行。

## DERP 队列与包丢失

复用此前的官方 Tailscale DERP 客户端库诊断程序，两个临时身份从本机经公网中继互相发送，每方向 4096 个 1024 字节合成包。服务端公开证书按既有证书指纹核对，不读取节点私钥。它是 DERP 合成测试，不是 Sunshine 视频，也不是独立 iroh QUIC。

| 发送目标 | 每方向数据量 | 正向有效速率 / 缺失 | 反向有效速率 / 缺失 |
| --- | ---: | --- | --- |
| 5 Mbps | 4 MiB | 4.981 Mbps / 0 包 | 4.980 Mbps / 0 包 |
| 25 Mbps | 4 MiB | 6.266 Mbps / 1882 包（45.947%） | 6.196 Mbps / 2221 包（54.224%） |

25 Mbps 测试前后读取 tc 自身的 DERP 计数：`derp_packets_dropped{reason="queue_head",kind="other"}` 恰好增加 4103，字节计数增加 4,201,472。客户端缺失 1882 + 2221 = 4103 包，每包 1024 字节，完全吻合。批量接收、转发和丢弃字节数也闭合；另有少量探测及其他已有节点流量，未混入这组相等关系。

由此确认这轮高码率缺失发生在 DERP 发送队列。结合独立 TCP 对照，不能只归咎于 Moonlight 或将它当成纯解码问题；当前公网方向承载不足会带来队列压力。扩大缓存不能增加已测得的公网吞吐，也不作为本轮优化措施。尚未更改队列、内核网络参数、Tailscale 或 DERP 配置。

一次新临时身份的预热往返曾在发送批量数据前超时，已明确排除，不计入吞吐或丢包样本。上表 25 Mbps 来自记录保留的一次重新运行，不能把诊断程序顶层的 `ok=true` 当成零丢包或码率达标；必须检查其中的具体收发计数。

## 实际 Windows 独立中继视频

本机已配对的开发客户端连接 winserver，强制使用 `https://101.43.203.147:33449/` 独立中继，H.264 / 1920×1080 / 请求 30 FPS / 外网码率上限 5 Mbps / 静音。winserver 自有虚拟屏中运行有期限的 30 FPS 图形窗口，未向 OPPO 发起连接。临时关闭本机配置自动同步以免传播测试配置，结束后恢复。

测量窗口 60.436 秒，图形源绘制频率恰为 30.0 FPS；客户端记录 3383 次 render_return，约 55.960 FPS，完整一秒窗口最少 48 次。帧间隔 P95 26.513 ms、P99 31.149 ms，最大 51.531 ms，超过 50 ms 共 1 次。统计显示网络丢帧 0.00%、抖动丢帧 0.00%，逐帧记录中有 2 次 `pacer_backlog` 丢弃，区别于网络包缺失。

现有服务端 minimum_fps_target=60，会使编码和渲染数量高于图形源和请求值；额外帧不能证明独特画面达到 60 FPS。本轮未修改此设置，也未测物理扫描呈现。图形窗口虽持续运动，平均编码有效载荷仅约 0.694 Mbps，不能当成 5 Mbps 饱和、高运动视频或 4K 验收。

本次首帧 render_return 为 11822.544 ms，仍然慢：

- 客户端原生进程开始前约 491.663 ms，进入串流连接前的准备约 8476.219 ms。
- 其中已记录的主机显示准备请求为 5038.920 ms，worker 为 4997.031 ms；原因为 `virtual_monitor_change_required`，走 PowerShell 更改虚拟屏的路径。
- 串流协议握手约 632.452 ms；协议就绪后等待首包约 2208.138 ms。
- 首包后组帧、解码及渲染提交合计约 14.072 ms。

这是一个明确的虚拟屏分辨率变更样本，不能与之前物理屏样本直接解释为回归或稳定上限。服务端准备和首包等待仍需继续优化，不能宣布初次连接耗时已解决。

结束后核对：原生会话正常退出，图形源窗口已关闭、临时任务已删除；设备配置逐字段恢复，自动同步和 statistics 开关恢复；物理屏及自有虚拟屏的尺寸、位置、刷新率和旋转均恢复。统计有 trace_end，分析无缺失警告，已删除用完的原始日志，仅保留当前分析所需的摘要、帧表与时间线。
