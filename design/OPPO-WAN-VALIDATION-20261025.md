# OPPO 手机流量热点实测（2026-10-25）

用户确认 OPPO 接手机流量热点，Tailscale IP 为 100.90.74.73，无线调试端口 41513。用户允许弱网卡顿，本轮优先验收连接、远程操作、取消与恢复；1080p30 的持续性能及局域网另行验收。初始安装为正式版 0.2.7 / code209、非 debuggable，三台主机配对保留。测试静音，不暂停业务。

## 已复现并修改

1. 正式版首次请求被主机返回 HTTP 400：`Invalid or unsupported initial display source`。Android 先对 GDI 屏幕名做 URL 编码，再交给要求原始查询的 `HttpUrl.Builder.query()`，百分号被二次编码。改为传入已严格验证的原始屏幕名。真实 pinned mTLS 请求回归覆盖完整 NvHTTP 路径；原有只检查拼接字符串的单测不能发现该问题。
2. 首帧前致命错误原先留在模态窗口，控制接口仍表现为正在连接。现在通过已有清理流程返回设备页，并保留错误状态；不会把证书、解码等致命错误当作可无限回退的网络错误。
3. 已建立的串流中断后，还会等待额外的待启动请求取消 HTTP 确认。弱网下可能卡住清理，出现“上一会话清理超时，已停止自动重连”。现在原生 `connectionStarted`（RTSP 建立完成）将本次待启动请求标记为已交接。之后仍等待本地原生线程清理，但不再依赖多余 HTTP 往返。首帧前未知请求仍要求按次取消确认；迟到的清理失败不能覆盖已确认的交接。此项实机复验进行中。
4. 正式 APK 无法使用调试版 `run-as` 导出统计。增加现有回环鉴权下的已结束统计导出，只允许固定统计文件、验证 `trace_end`，提供长度和 SHA-256；工具独立校验。分析完成确认必须匹配原文摘要，下一次录制前清理，未确认的调查材料保留。

## 当前实际结果

0.2.8-preview.1 / code210 覆盖安装后，原配对和客户端身份保留。强制 Tailscale 的 OPPO → winserver 已收到真实视频：初始屏幕选择在捕获前获主机确认，首个 `render_submit` 距连接动作 **6590.024 ms**，Surface 回调共 27 帧、零统计丢失。Surface 时间戳不等于物理屏幕扫描时间。

同次主机闭合记录共 179 次编码输出和 179 次 `send_end`，输出跨度 5.820204 秒，零 `send_error`、零记录丢失。平板统计持续约 32.889 秒，收到和提交 27 帧，随后进入恢复。截图显示接收/呈现约 0.49 FPS、平均网络延迟约 4896 ms、抖动约 6920 ms，最终弹出清理超时。发送调用成功不证明网络交付；不能据此宣称外网可正常使用或 30 FPS 已通过。

本次请求使用 1920×1080、30 FPS、原 25 Mbps 画面码率，主机实际使用 libx264。测试影片源也存在启动/播放丢帧，因此本轮仅作为连接、弱网和恢复故障证据，不作为持续帧率基线。影片及其限时任务已正常退出并移除。

新的恢复修复候选为 0.2.8-preview.2 / code211：151 项 Android JVM 测试、33 项共享核心测试通过，Release / 非 debuggable、签名保持不变。候选已覆盖安装，客户端身份及三台配对保留，仍未正式发布。APK SHA-256 为 `f984231dc50bce51436eef7682c440dcd8fe4059a61e8a23c4552315cf20c52d`。

winserver 两条路径均核对了测试窗口实际收到的主键 down/up 各 2 次、次键各 1 次、滚轮 delta 120、拖动移动 12 次，结束无按住的键。主机鼠标交换状态为 1，客户端补偿有效。分类悬浮栏、缩放/重置操作可调用，声音关闭且 `audioPackets=0`。中继／Tailscale 静态操作末段显示约 29.0／28.5 FPS，延迟约 111／78 ms；这些值不证明自然动态画面的稳定帧率。

首帧前取消时仍为 connecting，约 2258.582 ms 清理后立即重试并收到视频。取消记录包含一次 `http_resume`，随后按次取消 HTTP 耗时约 527.643 ms；不能把“首帧前取消”进一步写成已经证明“在原 HTTP 请求内部取消”。已建立会话的记录含本地交接确认，正常断开没有额外的待启动取消 HTTP。此次压力观察没有再次断线，**自动恢复的真实断线复验仍未完成**。

重试的 13.250 秒样本中，选路结束在 1.364 秒，原生移交在 6.470 秒；移交前 apps 阶段仍有约 5.106 秒未细分，不能把同时存在的多条后台 3 秒 serverinfo 探测直接相加归因。之后显示准备耗时 2.511 秒，resume HTTP 耗时 0.604 秒。下一步补应用列表获取／TLS 初始化和主线程移交的独立统计，继续调查首帧。

共 10 份设备记录均有 `trace_end`，零记录丢失。测试源、输入窗口及各自限时任务均已退出并删除；三台设备所有连接字段与测试前逐字段一致，自动同步恢复原值，客户端身份及三个配对保持。claw 再用原配置准备显示，选中原有 1920×1080 HyperVMonitor，原有自有主虚拟屏仍为 3840×2160；本轮未调整其模式。
