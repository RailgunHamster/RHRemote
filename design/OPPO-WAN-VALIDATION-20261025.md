# OPPO 手机流量热点实测（2026-10-25）

用户确认 OPPO 接手机流量热点，Tailscale IP 为 100.90.74.73，无线调试端口 41513。用户允许弱网卡顿，本轮优先验收连接、远程操作、取消与恢复；1080p30 的持续性能及局域网另行验收。初始安装为正式版 0.2.7 / code209、非 debuggable，三台主机配对保留。测试静音，不暂停业务。

## 已复现并修改

1. 正式版首次请求被主机返回 HTTP 400：`Invalid or unsupported initial display source`。Android 先对 GDI 屏幕名做 URL 编码，再交给要求原始查询的 `HttpUrl.Builder.query()`，百分号被二次编码。改为传入已严格验证的原始屏幕名。真实 pinned mTLS 请求回归覆盖完整 NvHTTP 路径；原有只检查拼接字符串的单测不能发现该问题。
2. 首帧前致命错误原先留在模态窗口，控制接口仍表现为正在连接。现在通过已有清理流程返回设备页，并保留错误状态；不会把证书、解码等致命错误当作可无限回退的网络错误。
3. 已建立的串流中断后，还会等待额外的待启动请求取消 HTTP 确认。弱网下可能卡住清理，出现“上一会话清理超时，已停止自动重连”。现在原生 `connectionStarted`（RTSP 建立完成）将本次待启动请求标记为已交接。之后仍等待本地原生线程清理，但不再依赖多余 HTTP 往返。首帧前未知请求仍要求按次取消确认；迟到的清理失败不能覆盖已确认的交接。此项实机复验进行中。
4. 正式 APK 无法使用调试版 `run-as` 导出统计。增加现有回环鉴权下的已结束统计导出，只允许固定统计文件、验证 `trace_end`，提供长度和 SHA-256；工具独立校验。分析完成确认必须匹配原文摘要，下一次录制前清理，未确认的调查材料保留。

## 重连交接的系统级证据及修复

code213 的 `1792913911797-b7622621-042` 实测首帧 **3312.889 ms**、656 次解码输出、531 次渲染提交，应用列表约 316.055 ms；请求头至响应头 163.561 ms，同次服务端排队 **20 µs**、处理 **74 µs**。HTTP 记录只有连接自己的 applist、serverinfo 和 launch，其他设备的并行探测为 0。它与前一慢样本不是恒定网络条件的单因素对照，不能把全部提速归于暂停发现，也不能补证旧样本的服务端耗时。

该会话随后遇到非注入的 `-1` 终止，成功清理和重新选路，却在 `1792913959142-724fe7b6-c95` 的交接后无 `native_attempt`，15 秒后报“串流窗口未能接管连接”。Android 系统事件给出了确定原因：

```
1792913912.237 wm_create_activity  id=199020917 Game
1792913959.266 wm_new_intent       id=199020917 Game
1792913959.274 wm_finish_activity  id=199020917 Game
```

上游 Game 的 `singleTask` 将重连 Intent 交给旧实例；RHRemote 接着结束旧实例，而原有实现只在 `onCreate` 创建下一会话。改为 `standard` 后由已有 admission/recovery 保留保证唯一性，新实例在旧原生连接清理完成后接管。实机系统事件证实创建了不同 ID 的新 Game，再关闭旧实例；不是只延长超时或隐藏错误。

修复为 0.2.8-preview.5 / code214，154 项 Android JVM 测试通过，Release 签名不变；APK SHA-256 为 `1ea362d4f53ea32dfe9882782b665206143a724a6a8d1afc5313798460783ebd`。新增测试模式接口 `stream.test.interrupt`，要求已实际提交首帧且启用测试统计，明确记录 synthetic 标记；未启用或已在重连时拒绝注入，使用正常清理及重连路径。
