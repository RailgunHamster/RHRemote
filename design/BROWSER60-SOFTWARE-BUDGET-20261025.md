## 已知结果

去掉额外整帧复制后，新引擎在原生 1080p30 影片的约 150.962 秒完整窗口中，
新采集回调约 29.976 FPS，输出间隔 P99 41.865 ms、最大 57.220 ms，没有超过 100 ms 的输出断档。
转换平均 3.175 ms；客户端首次 render_return 为 2.352 秒。
这支持当前 Windows → winserver 的该次 1080p30 窗口，不代替长期、OPPO、claw、60 FPS 或 4K 验收。

旧引擎真实影片输入通过原定门槛后，默认 software / H.264 / LAN 25 Mbps 的远程输出为 56.214 FPS。
默认两个线程下，服务端颜色转换与软件编码在同一处理循环串行，
新输入帧两段相加平均 17.187 ms，约 49.47% 超过 16.667 ms。
这是当前 60 FPS 差距中已测到的具体预算问题；跨度包含执行、同步和调度，不能全称为 CPU 计算时间。

四线程限时试验中，该串行跨度降至 11.744 ms，输出约 60.344 FPS，
但影片源丢帧 4.048%、3646 个输出中有 184 个复用输入。
该轮只保留诊断，不能宣称稳定或独特画面 60 FPS，未永久应用四线程配置。

## 线程采样发现的额外整帧复制

software60e 在原双线程配置做一次约 30 秒 CPU 诊断。带 WPR 后源丢帧 12.429%，
保留为诊断，不能与无剖析轮比较帧率。录制已关闭、独立停止任务已删除，原配置保留。
ETL 为 165062936 字节，SHA256 `5424CA08264E6393B1A32A742F845009899642D446BA11EE5C53CBFC6FE881C5`。
原始头部丢失为零；7,297,985 个事件、3,248,750 个 StackWalk，原生栈读取零错误。
32,226 条编码／采集线程原始切换与 xperf 独立解码的线程、CPU、时钟全部对应，
64 个锚点偏差范围 0.9001 微秒。编码与采集指令样本分别有 9 / 2 个未匹配栈顶，保留缺口，未称为全部栈完整。

这一轮转换平均墙钟 8.343 ms，其中主线程调度在 CPU 的跨度为 8.055 ms、离 CPU 0.288 ms；
encode 平均 9.796 ms，其中调度在 CPU 1.681 ms、离 CPU 8.115 ms。
在 CPU 的调度区间仍可能包含 ISR / DPC，不能全称为转换代码实际执行时间，
也不能把编码线程正常等待并行工作线程的时间全部当作调度故障。
该区别遵循 [Windows CPU 分析中的线程与中断模型](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis)。

另选 1507 个 ucrtbase 内存操作指令样本，全部在相同原始 QPC、CPU、载荷 PID / TID 和栈顶地址对上；
其中 1496 个对应实际 `sws_frame_start → av_frame_ref → frame_copy_video → image_copy_plane`。
实际映像哈希、加载基址、尺寸与 PE 校验和一致，rundown 的时间戳为零，明确保持未知；
全映像读取器另有两条其他记录无法解码，未隐去。

核对精确运行二进制及 DWARF：`image_copy_plane` 内联到 `av_image_copy`，
实际返回 RVA `0x52fe9e` 前是 `0x52fe99` 的五字节 `e8 a2 ec 3f 01`。
它调用 RVA `0x192eb40` 的 thunk，再经静态 IAT `0x253d720` 导入 `memcpy`。
所选 25 字节逐行复制循环 SHA256 为 `0F5F454E5B847CA3E3B2E87DE13D4A3A4CC53D2A18FB691D9339349213928726`。
这是实际机器码中的复制循环，不是私有驱动函数命名或对实时 IAT 的内存读取。
样本数不等于复制时长。

当前输入 AVFrame 只有借用的 `data` 指针，没有 `buf[0]`；
精确固定版本 FFmpeg 的 legacy `sws_frame_start` 调用 `av_frame_ref`，
后者在非引用计数输入上分配并复制整帧，再做原有转换。
因此找到了一处不必通过降低画质来减少的额外工作。

优化代码用 `rhremote_sws_input.h` 为具备已知容量、零尾部填充及真实共享所有者的 BGR0 捕获创建只读引用；
FFmpeg 引用持有原图像生命周期，正常返回和失败保留路径都不会提前释放像素。
Windows RAM 捕获补齐 64 字节零尾部；其他未提供容量或所有者的后端保留原复制路径。
原滤镜、颜色转换、编码预设及线程默认不变，另修正该分配路径中数组释放的 `delete[]` 配对。

本地实际链接固定版本 FFmpeg，6 项所有权／异常检查及 12 种真实 swscale 组合通过；
每种组合连续换三帧，1 / 2 / 4 线程、4:2:0 / 4:4:4、缩放／不缩放的活动像素均逐字节一致。

## 编码等待对应到工作线程信号

继续离线分析同一 software60e ETL，没有再启动录制或媒体会话。
7319 条目标为编码主线程的 ReadyThread 经 TDH 解码后，与独立 xperf 的时刻、CPU、目标线程逐一一致；
事件头的上下文 PID / TID 均为 `UINT_MAX`，没有把它当作有效身份。
实际信号线程来自相同触发 QPC / CPU 的原始 StackProcess / StackThread，所有片段身份一致；
xperf 有一条上下文标签未知，其余已知标签亦相符。

该编码窗口离 CPU 共 13090.152 ms，其中约 12025.207 ms 对应 x264 分片信号、
1049.682 ms 对应 x264 线程池信号；两类合计约 99.883%。
信号至主线程重新被调度平均分别为 0.029 / 0.030 ms，P99 为 0.081 / 0.207 ms，
仍有最大 4.368 / 3.684 ms 的个例。此处定位的是唤醒路径，
不等同于全部等待时间都在进行 CPU 计算，也不能把正常同步本身称为故障。

编号 2400 的 encode 调用为 22.352 ms，其最长一次离 CPU 等待为 12.4173 ms。
发出该分片信号的工作线程 TID 36572 在信号前的 12.3921 ms 内持续被调度在 CPU 上，
信号至主线程恢复只有 0.0252 ms；另一条分片信号线程 TID 23668 同窗口调度在 CPU 0.9479 ms、
等待 11.4442 ms。整个该次 encode 内两条线程调度在 CPU 分别为 16.5391 / 4.9606 ms，
Ready 至运行延迟分别只有 0.0140 / 0.0114 ms。

两条工作线程新增的 10028 条原始切换及 4420 条 ReadyThread 均逐一通过独立解码核对。
该次 encode 内选到的 15 个指令样本全部对上原始栈顶、QPC、CPU，实际 DWARF 指向
x264 的运动补偿、DCT / IDCT、量化、去块和 CABAC，包括 SSE、AVX2 与 BMI2 例程。
这些证据把该片段缩到软件编码工作线程路径，不能将其写成 GPU 排队或主线程恢复慢。
线程调度区间仍可能包含 ISR / DPC；没有逐周期 PMU、内部 job 身份和宏块坐标，
不能从单个带剖析的帧直接推断整段负载、固定的分片划分原因或独占 CPU 指令执行时间。

私有新增证据为 `native-encoder-waking-stacks.jsonl`、`encoder-wake-proof-v2.json`、
