# Android 配对阶段、重复操作与真实会话复验

记录 173，2026-10-31。只使用专用 emulator-5580 的隔离包 `com.rhremote.client.uicheck172`，产品版本由 172 更新为候选 173／391；包后缀表示隔离测试命名空间。正常 Android 129／347、Windows 日常客户端及 OPPO 不在本轮操作范围内，未公开发布。

## 已确认的问题与修改

真实 claw 配对等待中，页面已显示配对码，`admission.phase` 为 `pairing`，但 `connection.phase` 仍是 `identity`。主界面监听器特意跳过 pairing 回调，导致状态未随页面更新。现在由同一次阶段回调更新连接状态和配对页，移除回调前的重复绘制。

连接准备、配对、清理和已连接共用同一资源占用判断；原动作分发器却统一返回“请先断开当前连接”。现在按持有者和阶段说明当前操作：准备连接、等待配对、清理、清理失败待取消、恢复、恢复后启动串流，以及实际已有串流。按钮和 HTTP 接口继续经过同一个分发器，不放宽重复操作或取消完成前的占用保护，也不在提示生成中读取配置文件。

## 真实配对与重试

候选第一轮真实配对在到达 PIN 页前失败：LAN 的只读 serverinfo 请求报 `unexpected end of stream`，39 ms 内结束，不是本轮配对阶段断言失败。原失败状态和地址探测记录保留，未增加超时或把截断正文当成有效响应。

从这个失败页调用现有“重试配对”后，到达真实主机的配对等待；随后再次从设备页开始配对。两轮都验证页面和接口同时为 pairing，连接、重复配对、安装更新、网络诊断四项均以配对中的原因拒绝。取消分别为 815 ms、680 ms，主机待处理请求归零，设备选择和搜索保留，主机授权文件字节未变。没有向主机提交新的 PIN 确认，也没有创建额外授权。这些是候选第一版的实服务证据，最终候选的额外恢复阶段提示由后续回归及实际会话单独核对。

## 未响应与截断响应仍未解决

同一产品 172 的首次短测成功，首帧 10,816 ms；后续完整轮发生真实输入分发 ANR，原生记录止于 Game 创建早期，系统保留的 lastanr 没有 Java 线程栈，ApplicationExitInfo 的 trace 为 null。因此不能把别轮采样栈当作该次 ANR 的确切原因。

测试观察器原先仅在 close 时写采样，ANR 结束进程会丢失样本；现改为有界、逐条刷新日志，保留心跳、采样开始／结束与采样耗时。没有放宽超时或响应断言。只更新观察器而保持主 APK 172 字节相同后，完整会话通过，首帧 8,838 ms，取得实际非黑视频；仍有配置锁、系统调用和控件创建的主线程等待，最大心跳间隔 3,376 ms。这个不同负载下的成功轮不能证明 ANR 已修复，也不构成性能提升结论。

两次新的只读显示查询都在 Android FixedLengthSource 报正文提前结束；原始 TLS 与 Java HTTPS 对照的两组各两次正文长度匹配，预热后的正式调用成功。最终会话后再查时，原始 SSLSocket 收到 Content-Length=1542 的完整响应头，但正文为 0 字节；同轮 Java URL 和正式接口随后成功。该轮整项仍判失败，不能用最后一次成功覆盖前面的截断。这个样本将问题范围收窄到 JSON 解析之前的传输／响应结束链路，但仍未确定数据在何处丢失，不能直接归因 Android HTTP 库或把预热当作修复。

最终同轮正式接口返回的两条显示记录，与最初快照的全部 15 个字段相同，未新建显示器或调整模式。既有服务端关闭修正及其部署范围见 [EOF 记录](HOST-API-EOF-20261028.md)；本轮没有部署或重启任何服务。
